## 1. Technology Selection: Library Comparison

### 1.1. Next.js i18n (L1 + L2)

| Feature                  | `next-intl` (Chosen) | `react-i18next`                   | Native Next.js 14 i18n       |
| ------------------------ | -------------------- | --------------------------------- | ---------------------------- |
| **App Router Native**    | First-class support  | Requires wrapper / context        | Minimal / manual wiring      |
| **Server Components**    | Fully supported      | Client-focused / heavy hook usage | Custom implementation needed |
| **Type Safety**          | Strong               | Good with JSON types              | None                         |
| **Bundle Impact**        | Low (~3KB base)      | Medium (~12KB)                    | Zero (custom code)           |
| **Routing / Middleware** | Built-in middleware  | External routing needed           | Manual routing logic         |

**Decision**: **`next-intl`** for L1 + L2.

### 1.2. Widget Localization (L3) ⭐ MỚI

**Problem**: widget.js is **plain JavaScript** embedded in customer's page. It does NOT go through Next.js build pipeline, no TypeScript, no next-intl.

**Options:**

| Option                                 | Pros                                 | Cons                                                                         | Decision      |
| -------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------- | ------------- |
| **A: Lightweight translations object** | Simple, no dependencies, ~1KB/locale | Manual translation key management                                            | ✅ **Chosen** |
| B: Use next-intl in widget.js          | Type-safe, consistent                | widget.js must import next-intl → bundle pollution, doesn't work in plain JS | ❌            |
| C: Separate widget build pipeline      | Modern                               | Complex, requires separate build step                                        | ❌            |

**Decision**: Lightweight inline translations object for widget.js + **shared translations library** (`lib/i18n/widget-translations.ts`) for StandaloneChatUI + GroupChatView (which ARE in the Next.js pipeline and can import it).

**Key insight**: StandaloneChatUI and GroupChatView ARE React components in the Next.js pipeline → they CAN use `getWidgetTranslations()` from a shared library. widget.js is separate plain JS → duplicates the translations object (single source of truth issue).

**Mitigation**: Keep `lib/i18n/widget-translations.ts` as the **canonical source**. The widget.js copy is generated by a small script (`npm run gen:widget-i18n`) that reads the TS file and outputs a JS-compatible version.

## 2. Architecture Trade-offs: Platform vs Widget Locale

### 2.1. Platform Locale (L1 + L2)

| Option                    | Pros                          | Cons                                                 | Decision |
| ------------------------- | ----------------------------- | ---------------------------------------------------- | -------- |
| **A: Full Locale Prefix** | Clear URL structure           | Breaks workspace routing, requires 40+ route updates | ❌       |
| **B: Cookie-Only**        | Clean URLs                    | Poor SEO for public pages                            | ❌       |
| **C: Hybrid (Chosen)**    | SEO + clean workspace routing | Two mechanisms to maintain                           | ✅       |

### 2.2. Widget Locale (L3)

| Option                                             | Pros                                        | Cons                                                                      | Decision      |
| -------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------- | ------------- |
| **A: Per-bot JSONB `widget_settings.ui_language`** | Independent per bot, no migration, flexible | Must backfill existing bots                                               | ✅ **Chosen** |
| B: Inherit from platform locale                    | Simple, single source of truth              | Not independent — bot owner can't set different language, breaks use case | ❌            |
| C: Separate `bots.locale` column                   | Explicit column                             | Requires migration, less flexible than JSONB                              | ❌            |

**Decision**: Per-bot JSONB field in `widget_settings`. Backfill existing bots to `vi`.

### 2.3. Key Decisions Summary

| Decision                                                                           | Rationale                                                                                                      |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Widget locale **independent** from platform locale                                 | Bot owner serves customers with different languages; dashboard can be in one language while bot serves another |
| Use `widget_settings` JSONB (not new column)                                       | Already exists, flexible, zero migration for adding languages                                                  |
| Use `ELanguage` enum (existing)                                                    | Type safety, no new enum, consistent                                                                           |
| Default to `vi` when unset                                                         | Backward compatible, matches current behavior                                                                  |
| Shared translations library for React components + generated JS copy for widget.js | Single source of truth, DRY                                                                                    |

## 3. Middleware Composition Strategy

### Problem

Next.js 14 allows only **one** `middleware.ts`. Vielora already has complex logic:

1. Subdomain bot rewrites
2. Shopify CSP headers
3. Workspace path-based routing

### Solution

Instantiate `intlMiddleware` programmatically, execute **selectively** for public paths:

```typescript
const PUBLIC_PATHS = ["/", "/pricing", "/legal", "/about", "/contact", "/terms", "/privacy"];

if (isPublicPath) {
  const response = await intlMiddleware(request);
  return withShopifyCsp(response);
}
```

Widget routes (`/chat`, `/public-bot`) and API routes are **NOT** in PUBLIC_PATHS → untouched.
